# 现有项目迁移至按履约释放 PRL 的 V2：审查方案

状态：**供审查，尚未执行迁移，也未切换线上合约。**

本方案针对现有 Sepolia 测试项目。V2 的比例释放核心合约、供应商提款 API/UI 和本地测试已在开发；本方案所列的余额导入、迁移协调器、买家授权、双版本路由尚需实现并演练，不能把核心 V2 测试通过理解为迁移已准备广播。

## 1. 目标与不可改变的承诺

迁移后保持原项目 UUID、Launch ID、Provider ID、供应商钱包、模型及其 revision、credit 单价、发行承诺总量和买家实际未消费余额。Google/钱包身份绑定继续有效，不要求买家重新付费，不重置原 stake 的时间和验收历史。

PRL 规则：

`累计已解锁 = floor(初始质押 × 真实供应商已履约并结算的 credits / 固定发行承诺总量)`

`Locked = 初始质押 − 累计已解锁`

`Free = 累计已解锁 − 已提取`

`Returned = 已提取`

失败请求、试用、未结算请求、公共池代交付、迁移时旧 credits 的注销，均不能增加履约量。页面只把已最终确认的结算计为可操作的 Free。智能合约按同链 burn 状态计算权益；合约本身不能查询 RPC 的 `finalized` 标签，链重组时 burn/提款按同一条链的状态一起回滚。

## 3. 为什么不能直接搬 PRL

根据现有合约代码：

1. Stake V1 不是可升级代理，只有全额 `releaseStake`，没有部分提款。
2. `releaseStake` 把全部 tPRL 发给供应商，并把项目永久改为 Released。
3. Credits V1 的 `stakeContract` 是 immutable；其购买和重新存入要求旧项目仍为 Verified。仅搬 PRL 会让这些操作失败，后台/FRPC 的旧资格检查也会失效。
4. Credits V1 没有管理员搬走未消费 ETH 的函数。只有 burn 后累计的供应商收入可经供应商自己的 `claimRevenue` 领取。
5. Credits V1 的 `closeSales` 没有重新开启方法，不能把它当成可随意开关的临时维护按钮。
6. ERC-1155 钱包 token 可转移，旧合约也不能全局暂停。仅凭一次数据库快照复制余额，会造成重复权益风险。

因此不能通过改 MongoDB、改地址配置、先全额释放到钱包或直接给 V2 铸造余额来宣布迁移完成。

## 4. 现有项目的候选迁移机制

推荐仅在以下前置条件全部成立并获相关持有人授权后实施：**所有剩余 credits 都在旧 usage escrow、所有提款请求已处理/取消、所有在途生成和结算已完成、所有余额持有人签署 1:1 迁移同意。** 当前只读快照符合“没有托管外 tokens”的资产形态，仍须在执行窗口重新验证。

### 4.1 买家权益与旧 token 的处理

新 V2 保持同一项目键、1,000,000 固定供给上限、5,000 已发行计数、原模型和价格。只把实际剩余 4,951 credits 导入新 usage 余额；已经真实消耗的 49 不重新铸造。

为使旧余额不能继续使用，迁移协调器需要借用旧 `settleBatch` 接口注销旧托管余额。这**不是推理消费**：

- 使用独立、可验证的 `MIGRATION_RETIREMENT` usage-ID 命名空间及清单。
- 协调器发出独立迁移事件，列出旧 batch/usage IDs、新地址和余额导入根。
- UI/数据库把这些旧事件归类为“迁移注销”，绝不显示为用户生成消耗。
- 新质押的历史履约基线只导入真实 49，**不能导入注销后的旧总 burn 数 5,000**。
- 历史真实消费记录保留原合约、原交易及 request ID；新账户 usage 计数从导入余额开始，旧履约记录只用于只读历史和一次性历史履约基线。

这是旧不可升级合约的适配成本，必须在买家同意书及迁移报告里说明。不能接受该语义时，应选择第 10 节的自然结清方案，而不是偷偷用一次“假消费”替代迁移。

### 4.2 ETH 储备：由供应商临时预存，避免无担保复制权益

旧 ETH 无直接迁出接口，迁移前供应商须向隔离的 V2 迁移储备预存 **未消费 credits × 原单价**。按快照是 0.000004951 Sepolia ETH，另外自备 gas；实际金额按冻结后的最终清单计算。

旧托管余额注销会使其对价成为旧合约的供应商 receivable。迁移提交并最终确认后，供应商再从旧合约领取，回收对应的临时预存资金。旧有真实赚取收入须单列，不算新增利润。

- 新买家权益生效前，新储备必须已经足额；不能依赖供应商将来愿意把钱补回来。
- 预存款在迁移提交前应可由出资者撤回；提交后进入买家权益储备，不能随意退款给出资者。
- 不要求买家重新支付 ETH，也不从买家余额扣迁移 gas。
- 供应商后续领取旧收入并非整个迁移的原子步骤。若供应商不领取，资金仍在旧合约；新储备依然充足，买家权益不受影响，但供应商垫款未收回。
- 若有其他项目共享旧合约，必须按项目对账，不得动用其他项目的储备或收入。

### 4.3 PRL：在同一笔协调器交易中从 V1 交接到 V2

供应商预先对 V2 escrow 给出**精确的本项目初始金额** ERC-20 allowance。协调器取得仅为该项目、该次计划服务的迁移权限。

同一原子迁移交易内：

1. 最后验证旧状态、provider、token、amount、买家余额、授权和储备与清单完全一致。
2. 关闭旧项目销售；注销其旧托管 credits；把相同未消费权益导入 V2。
3. 调用旧 `releaseStake`，旧合约把 2,000 tPRL 发到原供应商。
4. V2 的专用 `importMigratedProject` 从该供应商拉入**同样的 2,000 tPRL**，校验实际到账差额。不能用普通 `stake()` 冒充供应商调用；普通 stake 的 sender 限制不适合协调器。
5. 导入旧验收状态、原始 stake 时间/截止时间、原始 provider 身份，并封存真实履约基线 49。
6. 校验所有资产守恒，封存 migration ID，撤销协调器临时权限，发出完成事件。

任一步失败，应整笔 revert，旧 `closeSales`、注销和释放也随之回滚，不能让 2,000 tPRL 留在供应商钱包而 V2 却声称已收到。不可把步骤 3、4 拆成“先释放，稍后自觉转入”。

## 5. 必须新增/调整的合约与后台功能

以下是迁移的实现门槛，当前核心 V2 原型还未全部包含：

| 模块 | 必需能力 |
| --- | --- |
| MigrationCoordinator | 固定旧/新地址、项目和 cap；计划哈希；所有持有人的授权；精确检查旧 accountState；一次性迁移 ID；协调原子资产交接 |
| Stake V2 迁移扩展 | 只允许协调器导入旧 Verified 项目；验证 legacy token/provider/amount/status；精确拉取 tPRL；导入历史履约基线；禁止重放、禁止提前全额释放 |
| Credits V2 迁移扩展 | 一次性导入余额/已发行数；不增加固定上限；储备足额；导入封存后不可改；历史消费与新消费分开；买家无需再次付费 |
| 维护状态 | 暂停目标项目的购买准备、试用/付费推理及提款准备；显式展示迁移进度；不把原有余额清零 |
| 多版本路由/monitor | 按项目选择 staking/credits 合约；新旧监控可并存；旧草稿、退款、历史交易不能因切换全局 env 丢失 |
| Migration ledger | 计划 ID、原始/新合约、最终 checkpoint、余额根、真实履约基线、旧注销 IDs、预存资金、每笔 tx 与 finality；日志不存密钥 |
| 前端 | 原余额、待迁移、等待 finality、已切换；Free/Locked/Returned 精确到 token decimals；供应商钱包签提款；历史交易保留原 explorer 链接 |

原项目的 UUID、Launch ID、Provider ID 和 FRPC route 不重建。数据库保留 `origin_staking_contract`、`origin_stake_tx_hash` 及迁移交易字段；更新活动合约归属。新资格检查必须验证新 escrow 的已导入状态，而不能绕过检查或把旧 Released 一律当作 Verified。

## 6. 执行顺序与人工检查点

### 阶段 A：实现与无资金演练

- 完成第 5 节扩展，代码审查后在 Anvil 上按真实持有人数量和状态演练。
- 用 Sepolia fork 固定 checkpoint 重放：验证 legacy 字节码/roles、余额、permit/allowance、gas 和完整原子交易。
- 先迁移独立的小额测试项目，覆盖余额、ETH 储备、PRL 交接、历史基线、后续购买/推理/burn/Free/提款及余额不足/重放/回滚。
- 新合约部署、角色配置与地址清单审查；**不改线上默认地址**。新地址目前未批准/部署用于实际迁移，签名清单中不得使用占位地址。

### 阶段 B：征得同意与预存

- 公布固定新地址、变更范围和维护窗口。两个余额持有人都需签署账户自己的迁移授权；平台测试钱包可以单独处理，人类买家钱包须由本人确认。
- 买家签名至少绑定：chain ID、项目键、旧/新合约、原 checkpoint、旧剩余余额、新余额、价格/单位/供给、计划哈希、nonce、expiry。
- 供应商确认精确 tPRL allowance 和临时 ETH 预存。gas 单独展示并模拟，不承诺固定费用。
- 不要求私钥/助记词，不使用无限 allowance，不以 Google 登录替代钱包授权。

### 阶段 C：冻结与最终快照

- 暂停目标项目的应用写入；等待所有已发请求、保留额度、已签原始结算交易和 pending burns 得到明确结果及 finality。未知/中断请求须先人工对账，不能直接删除 reservation。
- 暂停相应 settler，查验并处理旧已签交易；按权限清单暂撤旧 settlement/withdrawal approver 的并行写权限，协调器除外。若共享合约有其他活动项目，先完成并行路由方案，不能误停它们。
- 所有旧提款 pending/approved 均须取消/完成并重新入 escrow；钱包 token 总数必须为 0。任何持有人不配合时不进入提交阶段。
- **此时不要提前调用不可重新开启的旧 `closeSales`**。它放在最终原子交易内。
- 选新的 finalized block number/hash，重算资产及授权清单。直接合约购买/存入仍可能发生；最终协调器须逐账户、总 issued 和状态再次断言，发生变化就整笔拒绝、重新盘点和签署，不能吞掉新增余额。

### 阶段 D：原子提交与 finality

- 执行第 4 节唯一原子迁移交易，保存 tx hash，立即显示维护/确认进度。
- 交易失败：保持/恢复旧状态，不创建“成功迁移”的数据库余额。
- 已打包但未 finality：维持维护，不开放买家 API、新销售或 PRL 提款。重组时重查原交易和同一 migration ID，不盲目重放新计划。
- 达到 canonical finality 后，核对新 PRL 实收、每个新 usage 余额、ETH 储备、已发行/未发行数、历史履约基线及一次性标志。

### 阶段 E：切换与复验

- 在数据库事务内切换目标项目的活动合约归属和新 ledger epoch；保留旧记录为只读历史。新 account 的 available 计算只使用新 ledger；不得把旧已消费再扣一次。
- 先对同一 FRPC route 做只读和小额真实调用验收；恢复目标 API、settler 和销售。新项目默认走 V2；其他旧项目继续按自己的旧合约处理。
- 检查历史基线只计算真实 49；注销的 4,951 没有误触发 PRL 释放。
- 供应商可在 V2 提取已最终确认的 Free。按本快照，初始示例应是 Locked 1,999.902、Free 0.098、Returned 0 tPRL。
- 再用少量新 credits 真实生成、等待 burn finality，验证 Free 精确增加、提款后 Returned 增加且剩余服务正常。
- 最后供应商领取旧合约 receivable，并核对其中垫款回收与原 earned revenue。关闭旧批准角色与临时导入入口，归档清单。

## 7. 回退边界

- **原子提交前**：可取消计划、恢复后台服务/可逆角色、退回未承诺的预存资金。不得以提前 closeSales 换取假“可回滚”。
- **原子交易 revert**：链上资产交接不生效；按 receipts 和 manifest 对账再恢复服务。
- **交易已最终提交后**：旧 Released、旧 credits 注销均不可逆。不能通过回滚数据库/二进制回到旧系统。此后只能暂停写入、保留已确认权益，并修复/向前迁移新系统。
- 因此生产资金不能仅依赖“有数据库备份”来保证安全；必须先完成 fork/小额演练。提现后转到供应商的钱不能被当作可随意撤回。

## 8. 放行验收清单

必须全部满足：

- [ ] 当前最终快照、all-holder 枚举与 ERC-1155 TransferSingle/TransferBatch、购买、存入、提取、burn 事件相符。
- [ ] `issued = locked + wallet tokens + true burned`，没有未结算请求或已批准提款。
- [ ] 全部剩余余额持有人的授权有效；任何余额变化导致 abort。
- [ ] 旧钱包 tokens 为 0；否则先 redeposit 或拒绝本次迁移。
- [ ] 新 ETH 储备足额，旧项目收入/储备及其他项目资产分开。
- [ ] 原子 tPRL 差额检查通过，初始金额/provider/token/time/identity 不变。
- [ ] 新发行上限、已发行数、未发行数、价格、模型及使用单位保持一致。
- [ ] 导入基线为真实履约量，不包含迁移注销；重复提交不重复导入/解锁。
- [ ] V2 无可绕过比例规则的管理员全额 release；提款仅供应商签名。
- [ ] finality、reorg、失败、nonce 重用、gas 不足、错误签名/金额和导入中断均有测试。
- [ ] 双版本 monitor/FRPC/账本与 UI 通过真实验收；旧草稿、退款和已购 credits 无丢失。
- [ ] 具体迁移地址、资金上限、授权、维护窗口和不可逆提交步骤经人工审核。

## 9. 明确停止条件

持有人拒绝授权、钱包 token 无法归集、账本不一致、在途请求无法对账、预存不足、出现其他未覆盖的旧项目、checkpoint 变化、角色/代码不匹配，任一项都停止迁移，保留旧资金与服务。不能为了上线 Free 按钮临时放开旧 `releaseStake`。

## 10. 不接受上述适配成本时的替代方案

保留当前 V1 项目自然结清，V2 用于新项目。旧 credit 在旧合约中继续正常使用，PRL 保持原规则；等没有任何买家权益后，再单独审核结束旧承诺、全额释放和建立新项目。这不立即满足旧项目部分提款，但不需要重新解释旧 settlement 事件或临时垫付。

本方案的推荐执行路径是第 4–8 节的受控迁移，**前提是接受临时预存、全体持有人同意和“迁移注销不算履约”的明确区分**。当前只完成只读盘点及 V2 核心开发/测试，没有执行该路径。
